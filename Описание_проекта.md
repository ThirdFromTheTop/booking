1. НАЗНАЧЕНИЕ И АРХИТЕКТУРНЫЕ ПРИНЦИПЫ (CLEAN ARCHITECTURE & DDD)
Разработанное программное обеспечение представляет собой контейнеризированную информационную систему автоматизации процессов распределения ресурсов и учета инвентаря услуги проживания (отели) и перевозок (авиарейсы, ж/д поезда).

В основе проектирования системы лежит тандем Clean Architecture (Чистой архитектуры Роберта Мартина) и Domain-Driven Design (DDD). Главный принцип данной архитектуры — изоляция центрального ядра бизнес-логики (домена) от внешних инфраструктурных факторов, таких как веб-фреймворки (Spring Boot), контур безопасности (Spring Security), СУБД (PostgreSQL) или библиотеки сериализации (Jackson).

Вся ключевая бизнес-логика написана на чистой Java без использования сторонних аннотаций, что обеспечивает независимость системы от изменения сторонних технологических стеков и высокую тестируемость кода. Зависимости в проекте направлены строго извне вовнутрь (внешние слои знают о внутренних, но ядро полностью изолировано).

2. ОПИСАНИЕ АРХИТЕКТУРНЫХ СЛОЕВ
Программный комплекс разделен на три независимых слоя, взаимодействие между которыми организовано через механизм Портов (интерфейсов домена) и Адаптеров (инфраструктурных реализаций).

2.1. Слой domain (Изолированное бизнес-ядро)
Находится в центре архитектуры и не содержит импортов из библиотек Spring, Hibernate или Jackson.
* Доменные модели (Domain Models / Entities): Классы BookableItem, Booking и User. Они инкапсулируют бизнес-правила и следят за соблюдением бизнес-инвариантов. Логика конкурентного списания и возврата мест (reserveSeats и releaseSeats) находится внутри самого объекта инвентаря, предотвращая порчу данных. Расчет стоимости заказа (calculateTotalPrice) также инкапсулирован внутри модели бронирования.
* Порты домена (Domain Ports): Чистые Java-интерфейсы ItemDomainRepository и BookingDomainRepository. Они декларируют требования бизнеса к хранилищу данных, ничего не зная о базах данных.
* Интеракторы (Use Cases): Класс BookingUseCase. Координирует выполнение сквозных бизнес-сценариев (запуск транзакции бронирования, проверка остатков, вызов доменных инвариантов и сохранение).

2.2. Слой presentation (Адаптеры представления)
Отвечает за взаимодействие с пользователем по REST-протоколу. Содержит BookingController и AuthController.
* Функции слоя: Принять HTTP-запрос от фронтенда, распарсить входящий JSON, извлечь из зашифрованного JWT-токена личность пользователя (userId), передать чистые примитивные данные на выполнение в доменный BookingUseCase и вернуть стандартизированный ответ.

2.3. Слой infrastructure (Технические детали реализации)
Самый низкоуровневый внешний слой, содержащий конкретный технический стек.
* СУБД и ORM: Содержит JPA-сущности (BookingEntity, BookableItemEntity, UserEntity), размечающие таблицы СУБД PostgreSQL 15. Здесь же находятся адаптеры репозиториев (BookingDomainRepositoryImpl, ItemDomainRepositoryImpl), реализующие порты домена с помощью Spring Data JPA и Hibernate. При старте приложения Hibernate автоматически генерирует SQL-таблицы в Postgres на основе этих сущностей (ddl-auto: update).
* Безопасность (Security): Содержит конфигурацию Spring Security, глобальные настройки CORS-шлюзов (разрешающие запросы из браузера) и перехватчик JwtAuthFilter, валидирующий JWT-токены при каждом запросе к защищенным CRUD-маршрутам.

4. СЦЕНАРИЙ РАЗВЕРТЫВАНИЯ И КОНТЕЙНЕРИЗАЦИЯ (DOCKER)
Проект полностью изолирован от хост-системы и разворачивается одной командой docker-compose up --build. Персистентность данных обеспечивается за счет именованного Docker Volume pg_booking_data.

4.1. Механизм Multi-stage Build в Dockerfile
Сборка образа бэкенда разделена на два изолированных этапа внутри Dockerfile:
1. Build Stage (Образ Maven): Принимает исходный код бэкенда и файлы фронтенда, скачивает зависимости проекта, компилирует байт-код и упаковывает систему в исполняемый бинарный .jar-архив. По завершении этапа весь исходный код уничтожается.
2. Production Stage (Образ JRE): Из первого этапа копируется исключительно готовый .jar-файл. Он запускается на легковесной виртуальной машине Java (Alpine Linux). Это снижает размер итогового контейнера приложения до ~150 МБ и закрывает исходный код от конечного пользователя.

4.2. Порядок инициализации инфраструктуры
1. Контейнер booking-db запускает PostgreSQL 15. Проводится проверка готовности порта 5432 через встроенную утилиту pg_isready.
2. После успешного старта СУБД запускается контейнер бэкенда booking-app.
3. Hibernate ORM на слое инфраструктуры сканирует JPA-сущности и самостоятельно генерирует SQL-таблицы, связи и индексы в базе данных.
4. Главный класс BookingApplication через встроенный CommandLineRunner выполняет первичную программную инициализацию (добавляет тестовых пользователей с безопасным хэшированием паролей по алгоритму BCrypt, свободные номера в отелях и авиарейсы).
5. Встроенный веб-сервер Apache Tomcat запускает REST API на порту 8080 и параллельно начинает раздачу статического фронтенда из папки static.
